This note records the conceptual jump from naive CUDA matrix multiplication to shared-memory tiling. For the basic matrix math, thread indexing, and row-major address calculations, see [Hello world in CUDA programming](/blog/hello-world-cuda/).

```cpp
// Shared-memory-tiled CUDA C++ matmul kernel -- the optimized counterpart to
// cuda_naive.cu. Shows the things Triton's tile abstraction hides -- explicit
// threadIdx/blockIdx -> element mapping, an explicit __shared__ SRAM tile you allocate
// and index by hand, and explicit __syncthreads() barriers between the "load into
// SRAM" and "compute from SRAM" phases.
//
// Each thread owns exactly ONE output element C[row, col]. Threads in a block
// cooperate to stage one BLOCK x BLOCK tile of A and one of B into shared memory at a
// time, sync, consume that tile from SRAM (not HBM) for BLOCK multiply-adds, sync
// again, then slide to the next K tile. This is the classic textbook CUDA
// shared-memory tiled matmul -- the direct ancestor of what Triton's tl.load /
// autotuned BLOCK_K in triton_tiled.py does implicitly. Compare against cuda_naive.cu,
// which does the exact same math with no shared memory at all -- every thread
// re-reads straight from HBM on every k.
#include <torch/extension.h>
#include <cuda_runtime.h>

#define BLOCK 16

__global__ void matmul_tiled_kernel(
    const float* __restrict__ A,
    const float* __restrict__ B,
    float* __restrict__ C,
    int M, int K, int N
) {
    // Explicit per-thread output coordinate -- the mapping Triton's compiler does for
    // you invisibly. Here you write it: one thread, one (row, col).
    int row = blockIdx.y * BLOCK + threadIdx.y;
    int col = blockIdx.x * BLOCK + threadIdx.x;

    // Explicit on-chip SRAM scratch buffers, one BLOCK x BLOCK tile of A and B at a
    // time. This is a REAL shared-memory allocation you control -- the thing Triton
    // has no direct primitive for.
    __shared__ float As[BLOCK][BLOCK];
    __shared__ float Bs[BLOCK][BLOCK];

    float acc = 0.0f;

    // Slide a BLOCK-wide window across K. Same shape as triton_tiled.py's K-loop, but
    // every HBM->SRAM transfer and every sync point is written out by hand.
    for (int k0 = 0; k0 < K; k0 += BLOCK) {
        int a_col = k0 + threadIdx.x;   // column this thread loads for A's tile
        int b_row = k0 + threadIdx.y;   // row this thread loads for B's tile

        // Phase 1: HBM -> SRAM. Each thread loads exactly one element of A and one of
        // B into the shared tile. Out-of-bounds threads (edge tiles) write 0.
        As[threadIdx.y][threadIdx.x] = (row < M && a_col < K) ? A[row * K + a_col] : 0.0f;
        Bs[threadIdx.y][threadIdx.x] = (b_row < K && col < N) ? B[b_row * N + col] : 0.0f;

        // Barrier: every thread in the block must finish writing its element before
        // ANY thread starts reading the tile -- without this, some threads would read
        // stale/uninitialized SRAM.
        __syncthreads();

        // Phase 2: SRAM -> compute. BLOCK multiply-adds, all reading from on-chip
        // shared memory (fast), not HBM (slow). Direct analog of triton_tiled.py's
        // `acc = tl.dot(a, b, acc, ...)`, but written as the literal scalar loop that
        // tl.dot compiles down to under the hood.
        #pragma unroll
        for (int kk = 0; kk < BLOCK; kk++) {
            acc += As[threadIdx.y][kk] * Bs[kk][threadIdx.x];
        }

        // Barrier: every thread must finish reading the CURRENT tile before any thread
        // starts overwriting it with the NEXT tile's data.
        __syncthreads();
    }

    // Phase 3: single write back to HBM, same as every other kernel in this repo.
    if (row < M && col < N) {
        C[row * N + col] = acc;
    }
}


torch::Tensor matmul_cuda_tiled(torch::Tensor a, torch::Tensor b) {
    TORCH_CHECK(a.is_cuda() && b.is_cuda(), "inputs must be CUDA tensors");
    TORCH_CHECK(a.dtype() == torch::kFloat32 && b.dtype() == torch::kFloat32, "inputs must be float32");
    TORCH_CHECK(a.is_contiguous() && b.is_contiguous(), "inputs must be contiguous");

    int M = a.size(0);
    int K = a.size(1);
    int N = b.size(1);
    TORCH_CHECK(K == b.size(0), "shape mismatch");

    auto c = torch::empty({M, N}, a.options());

    dim3 threads(BLOCK, BLOCK);
    dim3 blocks((N + BLOCK - 1) / BLOCK, (M + BLOCK - 1) / BLOCK);

    matmul_tiled_kernel<<<blocks, threads>>>(
        a.data_ptr<float>(), b.data_ptr<float>(), c.data_ptr<float>(), M, K, N
    );

    return c;
}

PYBIND11_MODULE(TORCH_EXTENSION_NAME, m) {
    m.def("matmul_cuda_tiled", &matmul_cuda_tiled, "Shared-memory-tiled CUDA matmul");
}
```

The one sentence I want to remember is:

> Both kernels assign one thread to one output element. Tiling does not reduce the arithmetic or make the output computation less parallel; it reorganizes input loading so threads in the same block can reuse data.

My confusion came from mixing three separate layers:

| Layer | Question |
|---|---|
| Output ownership | Which `C[row,col]` does this thread compute? |
| K traversal | Which part of the dot product is the thread processing now? |
| Data movement | Where do the A and B values come from? |

The naive and tiled kernels differ mainly in the third layer.

To avoid overloading the word “tile,” this note uses four specific terms:

| Term | Meaning | Where it exists |
|---|---|---|
| C output region | The `BLOCK × BLOCK` part of C assigned to one CUDA block | Logical region of global C |
| K slice | The current range `k0 .. k0+BLOCK-1` | A range of K indices, not a separate allocation |
| A/B global source region | The rectangular part of the original A or B tensor needed for the current K slice | CUDA global-memory address space; a load may be served by cache or device DRAM |
| `As`/`Bs` shared-memory tile | The block-private on-chip copy populated from that source region | Shared memory inside one CUDA block |

The A/B global source region is not a separately allocated tile sitting in HBM. It becomes a shared-memory tile only after the block's threads load it into `As` or `Bs`.

## Layer 1: output ownership is unchanged

Both kernels begin with the same mapping:

```cpp
int row = blockIdx.y * BLOCK + threadIdx.y;
int col = blockIdx.x * BLOCK + threadIdx.x;
```

Read it as:

```text
global output coordinate = block origin + local thread offset

row = blockIdx.y × BLOCK + threadIdx.y
col = blockIdx.x × BLOCK + threadIdx.x
```

`blockIdx` chooses a `BLOCK × BLOCK` region of C. `threadIdx` chooses one position inside that region. Together they identify the thread's one output element.

This remains true in both implementations:

```text
naive:  one thread → one C[row,col]
tiled:  one thread → one C[row,col]
```

Tiling does not turn many output threads into a smaller number of threads. It also does not assign one thread to each individual multiplication. In both kernels, one thread performs the complete K-axis dot product for one output.

## Layer 2: K traversal is sequential inside each thread

The naive kernel visits K one element at a time:

```cpp
for (int k = 0; k < K; k++) {
    acc += A[row * K + k] * B[k * N + col];
}
```

The tiled kernel visits the same K dimension one `BLOCK`-wide slice at a time:

```cpp
for (int k0 = 0; k0 < K; k0 += BLOCK) {
    // stage the current K slice
    // compute BLOCK terms from shared memory
}
```

For one thread, `k0=0`, `k0=BLOCK`, and `k0=2×BLOCK` happen sequentially. But all output threads have their own copy of this loop and run in parallel.

- C blocks in the same block row read the same region of global A.

The repeated loads may be satisfied by hardware caches rather than physical device DRAM. The logical CUDA guarantee is only that shared-memory reuse is local to one block.

This distinction is central:

```text
sequential: one thread moves across the K slices
parallel:   many threads and potentially many blocks do this independently
```

## Layer 3: tiling changes data movement

The naive kernel reads its inputs using global addresses during every K iteration:

```cpp
acc += A[row * K + k] * B[k * N + col];
```

Neighboring threads need overlapping data. Threads in the same output row reuse A values; threads in the same output column reuse B values. The naive source expresses those needs as separate global-memory loads.

This is the point where naive and tiled genuinely diverge, and the divergence is best understood as *how many coordinate systems the kernel needs.*

**Naive has one coordinate system.** `row` and `col` are fixed once, and `k` walks straight through global memory:

```cpp
int row = blockIdx.y * BLOCK + threadIdx.y;   // fixed for this thread, forever
int col = blockIdx.x * BLOCK + threadIdx.x;   // fixed for this thread, forever

for (int k = 0; k < K; k++) {
    acc += A[row * K + k] * B[k * N + col];   // reach straight into HBM, every k
}
```

One thread, one output element, one global `(row, col)`, and `k` indexes straight into HBM every time. There is nothing else to track.

**Tiled has two coordinate systems, nested.** The first is the same global `(row, col)` as naive — it still says which output element this thread owns, and nothing about it changes:

```cpp
int row = blockIdx.y * BLOCK + threadIdx.y;
int col = blockIdx.x * BLOCK + threadIdx.x;
```

The second is new: a *local* coordinate that means "my position inside the current `BLOCK × BLOCK` shared-memory tile," reusing `threadIdx.y` / `threadIdx.x` but with a different meaning than in the global calculation above. It first appears when a thread copies one value from global memory into its shared-memory slot:

```cpp
__shared__ float As[BLOCK][BLOCK];
__shared__ float Bs[BLOCK][BLOCK];

As[threadIdx.y][threadIdx.x] = ...;   // local coord: position inside this tile
Bs[threadIdx.y][threadIdx.x] = ...;
```

That's the only new idea in this layer: **the same `threadIdx.y`/`threadIdx.x` pair now also names a slot inside the tile, on top of what it already meant for `row`/`col`.** What eventually happens with that slot — sync, then a dot-product loop over it — is a separate step covered in the worked example below; this layer is only about *where the two coordinate systems come from*.

|  | Naive | Tiled |
|---|---|---|
| Who decides the output element | `(row, col)` from `blockIdx`/`threadIdx` | Same — unchanged |
| Where the K-loop reads from | Global memory (HBM), every iteration | Shared-memory tile, refilled from HBM once per `BLOCK` steps |
| Number of coordinate systems | 1 (global) | 2 (global for output, local for position-inside-tile) |
| Redundant global-memory traffic | Yes — overlapping rows/columns are re-fetched independently by each thread | No — one cooperative load per tile, reused via shared memory |

The naive kernel has no local frame because it never stages anything on-chip; there is nothing to have a local coordinate *into*. Tiling only needs one because it interposes a staging area between HBM and the arithmetic.

Put together, the tiled kernel splits each K-slice iteration into four steps, always in this order:

```text
1. load    — every thread copies one A value and one B value into As/Bs (global -> local)
2. sync    — wait until the whole tile is written before anyone reads it
3. compute — every thread walks the local frame to accumulate this slice's contribution
4. sync    — wait until everyone is done reading before the tile is overwritten
```

The worked example below walks these four steps in this exact order. The amount of matrix-multiplication arithmetic is essentially unchanged; the optimization targets global-memory traffic by making reuse explicit inside the block.

### Tile movement direction

### Step 1 — load: copy one global value into one local slot

For readability, define:

```cpp
int ty = threadIdx.y;
int tx = threadIdx.x;
```

The loading code is:

```cpp
int a_col = k0 + tx;
int b_row = k0 + ty;

As[ty][tx] = A[row * K + a_col];
Bs[ty][tx] = B[b_row * N + col];
```

The simplest way to read it is:

```text
A source = A[my fixed output row, k0 + my local x]
B source = B[k0 + my local y, my fixed output column]

A destination = As[my local y][my local x]
B destination = Bs[my local y][my local x]
```

For this thread:

```text
A source: A[row, k0+tx] = A[0, 2+1] = A[0,3]
B source: B[k0+ty, col] = B[2+0, 3] = B[2,3]

A[0,3] → As[0][1]
B[2,3] → Bs[0][1]
```

The local coordinate `(ty,tx)` does not replace the global coordinates. It connects the current thread to one position inside each block-owned shared-memory tile.

That was one thread in one block. The next question is what changes if a *different* block runs this exact same code. The `k0` in `a_col`/`b_row` isn't a per-thread value — it's the outer loop variable, shared by every block:

```cpp
for (int k0 = 0; k0 < K; k0 += BLOCK) {   // every block runs this loop independently
    int a_col = k0 + tx;                  // same k0, same tx → same a_col in every block
    int b_row = k0 + ty;                  // same k0, same ty → same b_row in every block
    As[ty][tx] = A[row * K + a_col];      // row is this block's own row — that's what varies
    Bs[ty][tx] = B[b_row * N + col];      // col is this block's own col — that's what varies
    ...
}
```

A few facts fall out of that:

- `a_col` and `b_row` depend only on `k0`, `tx`, `ty` — never on `row`, `col`, or `blockIdx`. At a given loop iteration, every block computes the *same* `a_col` and the *same* `b_row`.
- `blockIdx` only enters through `row` and `col`, which were fixed once at the top of the kernel (`row` from `blockIdx.y`, `col` from `blockIdx.x`).
- `A[row, a_col]` combines this block's own `row` with the shared `a_col`. `B[b_row, col]` combines the shared `b_row` with this block's own `col`.
- The destination slot `As[ty][tx]` / `Bs[ty][tx]` also depends only on `ty`/`tx`, so it's the same slot in every block — but each block writes it into its *own* private tile, not a shared one.

Two concrete blocks make this checkable. Both sit in block-row `y=0`, so both have `row=0`; block `(x=0,y=0)` and block `(x=1,y=0)` sit in different block-columns, so `col` is `1` and `3` respectively:

| | Block (0,0) | Block (1,0) | Same or different? |
|---|---|---|---|
| `row` | 0 | 0 | same (same block-row) |
| `col` | 1 | 3 | different (different block-column) |
| `a_col = k0+tx` | 3 | 3 | same — no `blockIdx` term |
| `b_row = k0+ty` | 2 | 2 | same — no `blockIdx` term |
| `A[row, a_col]` read | `A[0,3]` | `A[0,3]` | **same value, redundantly fetched** |
| `B[b_row, col]` read | `B[2,1]` | `B[2,3]` | different — `col` differs |
| Destination slot | `As[0][1]` / `Bs[0][1]` | `As[0][1]` / `Bs[0][1]` | same slot, but each in its own tile |

Both derivations start from the same loop iteration and the same formula, but each block runs it with its own `row`/`col` — there is no arrow crossing between the two panels because nothing does. Block `(1,0)` doesn't receive `A[0,3]` from block `(0,0)`; it *re-derives* it from its own `row=0` combined with the shared `a_col=3`, and just happens to land on the same value because both blocks are in block-row `y=0`.

The pattern generalizes: at any loop iteration, every block computes the same `a_col`/`b_row`, but each combines them with its own `row`/`col`. Depending on the grid layout, that can land on the same global value (as with A here) or a different one (as with B here). Either way, the destination is always the same local slot, just inside that block's own private tile.

This thread only ever writes **one** `As` entry and **one** `Bs` entry. With `BLOCK=2`, the whole block has four threads, and together they fill all four entries of each tile — no thread fills more than its own slot:

```text
T00 fills [0][0]    T01 fills [0][1]
T10 fills [1][0]    T11 fills [1][1]
```

### Step 2 — sync: wait for the whole tile

```cpp
__syncthreads();
```

At this point some threads may have already written their slot while others haven't. The barrier means: **no thread may move past this line until every thread in the block has reached it.** Only after the barrier is it safe to assume `As` and `Bs` are completely filled — this thread is about to read slots it did *not* write itself (`As[0][0]` and `Bs[1][1]`, from the step below), so it must wait for whichever neighbor writes them.

### Step 3 — compute: consume the whole tile, not just your own slot

Now the thread producing `C[0,3]` runs the dot-product loop over the local frame:

```cpp
for (int kk = 0; kk < BLOCK; kk++) {
    acc += As[ty][kk] * Bs[kk][tx];
}
```

For `ty=0`, `tx=1`, `BLOCK=2`, that expands to:

```text
As[0][0] × Bs[0][1]
+ As[0][1] × Bs[1][1]
```

This thread loaded only `As[0][1]` and `Bs[0][1]` in step 1 — but step 3 reads `As[0][0]` and `Bs[1][1]` too, which its neighbors loaded. That cross-reading is exactly the cooperation and reuse the naive kernel doesn't have: every thread loads once, but consumes `BLOCK` values that mostly came from someone else.

### Step 4 — sync: wait before the tile is overwritten

```cpp
__syncthreads();
```

The loop advances to the next `k0` right after this, and step 1 of the next iteration overwrites `As`/`Bs`. This second barrier means: **no thread may start overwriting the tile until every thread has finished reading it in step 3.** Without it, a fast thread could start step 1 of the next slice while a slow neighbor is still mid-loop in step 3, corrupting the values it's reading.

### The four steps together

```cpp
As[ty][tx] = ...;                 // 1. load
Bs[ty][tx] = ...;

__syncthreads();                  // 2. sync — tile is now complete

for (int kk = 0; kk < BLOCK; kk++) {
    acc += As[ty][kk] * Bs[kk][tx];   // 3. compute — read the whole tile
}

__syncthreads();                  // 4. sync — safe to overwrite next iteration
```

Every K-slice iteration repeats these four steps in this exact order. There is no valid order where compute happens before load, or where the second sync is skipped — the two barriers are asymmetric guards on the two directions of the same hazard: reading a tile too early, and overwriting one too soon.

## What reuse tiling provides

Shared memory belongs to one CUDA block:

```text
within one block
    → threads cooperatively load global A/B source regions into As and Bs
    → threads reuse those shared-memory values
    → duplicate global-memory loads are greatly reduced

across different blocks
    → each block has independent shared memory
    → the same A or B data may be loaded again
```

Hardware caches may serve some repeated loads between blocks, so a repeated global-memory instruction does not necessarily reach physical device DRAM. Logically, however, shared-memory reuse stops at the block boundary.

The sentence to remember is:

> Tiling reduces redundant input loads within a block, not necessarily across blocks.

## Why tiled loads need extra edge checks

The naive kernel checks its output coordinate once and is done:

```cpp
if (row >= M || col >= N) return;
for (int k = 0; k < K; k++) {
    acc += A[row * K + k] * B[k * N + col];   // k is always < K here — no further check needed
}
```

`k` never leaves `[0, K)`, so every address the loop touches is valid by construction. There's nothing to check inside the loop.

Tiling breaks that guarantee. It advances K in whole `BLOCK` chunks, and if `K` isn't a multiple of `BLOCK`, the last chunk doesn't end exactly at the matrix edge — it overshoots:

Every thread in the block still runs the same loading code, including the threads whose `a_col`/`b_row` land in the red zone. Without a check, those threads read past the end of `A` or `B` — undefined behavior. The fix is the ternary padding already in the kernel:

```cpp
int a_col = k0 + threadIdx.x;   // may be >= K in the final K slice
int b_row = k0 + threadIdx.y;   // may be >= K in the final K slice

As[threadIdx.y][threadIdx.x] = (row < M && a_col < K) ? A[row * K + a_col] : 0.0f;
Bs[threadIdx.y][threadIdx.x] = (b_row < K && col < N) ? B[b_row * N + col] : 0.0f;
```

Zero is a safe placeholder because it contributes nothing to `acc += As[...] * Bs[...]`.

One more consequence: an out-of-range output thread (`row >= M` or `col >= N`) still can't `return` early, because it must reach every `__syncthreads()` alongside its block. It participates in loading (writing zeros) and synchronizing, and only the final store is guarded:

```cpp
if (row < M && col < N) {
    C[row * N + col] = acc;
}
```

| | Naive | Tiled |
|---|---|---|
| What can go out of bounds | Nothing — `k` is loop-bounded | The last K-tile, and edge output blocks |
| Where the check lives | Once, before the loop (early `return`) | Inside every load, every K-slice iteration |
| What an out-of-range thread does | Returns immediately | Keeps loading zeros and hitting barriers; only the final store is skipped |

## Naive versus tiled: final comparison

| Question | Naive | Tiled |
|---|---|---|
| Who owns `C[row,col]`? | One thread | The same one thread |
| How is K traversed? | Sequential scalar `k` loop | Sequential `k0` slices, then local `kk` |
| Are output threads still parallel? | Yes | Yes |
| Where does the inner loop read? | Global A/B addresses | Block-private `As`/`Bs` shared-memory tiles |
| Does tiling reduce arithmetic? | No | No |
| What does it reduce? | Nothing explicitly | Duplicate input loads within a block |
| Can blocks share `As` or `Bs`? | Not applicable | No; each block owns separate shared memory |
| Edge handling | Early output bounds check | Checked, zero-padded shared-memory loads plus guarded final store |

## Review card

1. One thread owns one C element in both kernels.
2. Tiling does not reduce thread-level parallelism or the number of multiply-adds.
3. One thread traverses K slices sequentially; many output threads do this in parallel.
4. During loading, every thread copies one A value and one B value from global source regions into the block's shared-memory tiles.
5. `A[row, k0+tx] → As[ty][tx]`.
6. `B[k0+ty, col] → Bs[ty][tx]`.
7. During computation, the thread walks `As[ty][kk]` and `Bs[kk][tx]`.
8. Reuse occurs within a block; other blocks have separate shared memory.
9. A final partial K slice requires checked loads and zero padding in `As` and `Bs`.
10. Threads must not return before a `__syncthreads()` that their block peers will reach.

The complete mental model is:

```text
fixed output ownership
        +
sequential traversal of K slices
        +
cooperative load → synchronize → shared-memory reuse
```
