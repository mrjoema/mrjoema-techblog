I use CUDA and NVIDIA's software stack because they are the most widely used tools for GPU programming, but many of the underlying concepts also apply to platforms such as Apple Metal and Google TPUs.

## CPU and GPU execution

A CPU has a relatively small number of powerful cores designed for low-latency execution, complex control flow, and many different kinds of work. A GPU has many more, simpler execution units designed to perform the same operation across a large amount of data in parallel.

GPUs are not limited to matrix multiplication, but matrix operations are a particularly good fit for this parallel design. A matrix can be viewed as a collection of rows, where each row is a one-dimensional array. Because many output elements can be calculated independently, we can divide the output matrix into equally sized tiles and assign those tiles to CUDA thread blocks.

This division is a logical partition of the work, not a physical split of the tensor into separate memory allocations. In the naive kernel below, a `BLOCK x BLOCK` tile corresponds to one CUDA thread block, and each thread computes one element inside that tile.

## Code example

The code below implements a basic matrix multiplication. I will cover optimization in a separate post; here, I only show the essential code so that we can focus on the concepts.

```cpp
// Naive CUDA C++ matrix-multiplication kernel: no shared memory and no tiling.
// Every thread computes exactly one output element by reading directly from
// global memory on every step of the K loop. This is the GPU equivalent of the
// CPU triple loop: global-memory read -> multiply-add -> repeat K times -> one
// global-memory write.
//
// The defining flaw is that neighboring threads in the same block repeatedly
// fetch overlapping rows and columns of A and B. Nothing is staged on-chip and
// shared between them. A tiled implementation fixes this by cooperatively
// loading each BLOCK x BLOCK tile into shared memory once and reusing it.

#include <torch/extension.h>
#include <cuda_runtime.h>

#define BLOCK 16

__global__ void matmul_naive_kernel(
    const float* __restrict__ A,
    const float* __restrict__ B,
    float* __restrict__ C,
    int M,
    int K,
    int N
) {
    // Map this thread to one output coordinate: C[output_row, output_col].
    int output_row = blockIdx.y * BLOCK + threadIdx.y;
    int output_col = blockIdx.x * BLOCK + threadIdx.x;

    if (output_row >= M || output_col >= N) {
        return;
    }

    // Keep output_row and output_col fixed while k moves across the selected
    // row of A and down the selected column of B.
    float acc = 0.0f;
    for (int k = 0; k < K; k++) {
        acc += A[output_row * K + k] * B[k * N + output_col];
    }

    // Write the completed dot product back to global memory once.
    C[output_row * N + output_col] = acc;
}

torch::Tensor matmul_cuda_naive(torch::Tensor a, torch::Tensor b) {
    TORCH_CHECK(a.is_cuda() && b.is_cuda(), "inputs must be CUDA tensors");
    TORCH_CHECK(
        a.dtype() == torch::kFloat32 && b.dtype() == torch::kFloat32,
        "inputs must be float32"
    );
    TORCH_CHECK(
        a.is_contiguous() && b.is_contiguous(),
        "inputs must be contiguous"
    );

    int M = a.size(0);
    int K = a.size(1);
    int N = b.size(1);

    TORCH_CHECK(K == b.size(0), "shape mismatch");

    auto c = torch::empty({M, N}, a.options());

    dim3 threads(BLOCK, BLOCK);
    dim3 blocks(
        (N + BLOCK - 1) / BLOCK,
        (M + BLOCK - 1) / BLOCK
    );

    matmul_naive_kernel<<<blocks, threads>>>(
        a.data_ptr<float>(),
        b.data_ptr<float>(),
        c.data_ptr<float>(),
        M,
        K,
        N
    );

    return c;
}
```

## Code understanding line by line

In high-level code, we commonly use notation such as `matrix[matrix_row_index][matrix_column_index]` and let the compiler or runtime translate it into a memory address. In this CUDA kernel, we work with flat pointers and calculate the offset ourselves.

A contiguous two-dimensional tensor is stored as a one-dimensional sequence in row-major order. The generic flattening rule is:

```text
flat offset = matrix_row_index × matrix_column_count + matrix_column_index
```

These names describe positions in any matrix; they are not the kernel variables. In the kernel, the thread-owned coordinate is deliberately named `(output_row, output_col)`.

That is why the kernel accesses the three matrices using these expressions:

- `A[output_row * K + k]` for `A[output_row, k]`
- `B[k * N + output_col]` for `B[k, output_col]`
- `C[output_row * N + output_col]` for `C[output_row, output_col]`

### The host function: `matmul_cuda_naive`

The host function first validates its inputs:

- **Device validation:** both input tensors must live on a CUDA device.
- **Data-type validation:** the kernel accepts pointers to 32-bit floating-point values and performs FP32 arithmetic.
- **Contiguity validation:** each tensor must use the dense row-major layout assumed by the index calculations in the kernel.
- **Shape validation:** the inner dimensions must match, so an `M x K` matrix can be multiplied by a `K x N` matrix.


Matrix multiplication repeatedly takes the dot product of a row from matrix A and a column from matrix B. If A has shape `M x K` and B has shape `K x N`, the result C has shape `M x N`.

Therefore, we have the code below:

```cpp
int M = a.size(0); // Capture the row count of tensor A.
int K = a.size(1); // Capture the column count of tensor A.
int N = b.size(1); // Capture the column count of tensor B.

// Validate that A's column count equals B's row count.
TORCH_CHECK(K == b.size(0), "shape mismatch");
```

After confirming that the input shapes are compatible, we allocate the output tensor:

```cpp
/**
Dot product: C = A dot B
Given A(M, K) and B(K, N), so the output becomes C(M, N)
**/
auto c = torch::empty({M, N}, a.options());
```

Next, we define the CUDA launch configuration:

```cpp
dim3 threads(BLOCK, BLOCK);
dim3 blocks(
    (N + BLOCK - 1) / BLOCK,
    (M + BLOCK - 1) / BLOCK
);
```

`dim3` is CUDA's three-dimensional size type. With `BLOCK` set to `16`, `threads` describes a two-dimensional thread block containing `16 x 16`, or 256, threads. Each thread is responsible for calculating one element of `c`.

`blocks` describes how many thread blocks the grid needs. CUDA's x-axis covers the `N` output columns, while its y-axis covers the `M` output rows:

```text
blocks.x = ceil(N / BLOCK)
blocks.y = ceil(M / BLOCK)
```

Because C++ integer division normally rounds down, `(size + BLOCK - 1) / BLOCK` is used to round up. For example, 50 columns require `(50 + 16 - 1) / 16 = 4` blocks, giving enough threads to cover 64 columns. Threads that fall outside the actual matrix dimensions are discarded by the bounds check inside the kernel:

```cpp
if (output_row >= M || output_col >= N) {
    return;
}
```

Together, `blocks` and `threads` create a two-dimensional grid that covers every element of the `M x N` output matrix.

### The CUDA kernel: `matmul_naive_kernel`

This kernel contains the code executed by every CUDA thread. Because many threads run it in parallel, each thread must calculate the unique output element it owns.

```cpp
// Map this thread to one output coordinate: C[output_row, output_col].
int output_row = blockIdx.y * BLOCK + threadIdx.y;
int output_col = blockIdx.x * BLOCK + threadIdx.x;

if (output_row >= M || output_col >= N) {
    return;
}
```

CUDA uses the x-axis for columns and the y-axis for rows. `blockIdx` identifies a block in the grid, while `threadIdx` identifies a thread's local position inside that block:

```text
output_row = blockIdx.y × BLOCK + threadIdx.y
output_col = blockIdx.x × BLOCK + threadIdx.x
```

For the highlighted block, CUDA reports:

```cpp
blockIdx.x = 0;
blockIdx.y = 1;
```

The first thread in this block, `threadIdx = (0, 0)`, maps to the block's top-left output coordinate, `C[16, 0]`. The highlighted thread has `threadIdx = (1, 0)`, so its global coordinate is:

```cpp
output_row = blockIdx.y * BLOCK + threadIdx.y;
           = 1 * 16 + 0;
           = 16;

output_col = blockIdx.x * BLOCK + threadIdx.x;
           = 0 * 16 + 1;
           = 1;
```

Therefore, this thread computes `C[16, 1]`. Every valid combination of `blockIdx` and `threadIdx` maps to a different element of `C`, so the threads do not conflict when writing the output. Multiple threads may read the same values from A or B, but those shared reads are safe.

The bounds check handles threads in partially filled edge blocks. If a calculated `output_row` or `output_col` falls outside the `M × N` output, that thread exits without reading or writing memory.

### Computing the dot product using flat memory

After choosing its output coordinate, the thread computes the dot product between row `output_row` of A and column `output_col` of B:

```cpp
// Keep output_row and output_col fixed while k moves across A and down B.
float acc = 0.0f;
for (int k = 0; k < K; k++) {
    acc += A[output_row * K + k] * B[k * N + output_col];
}

// Write the completed dot product back to global memory once.
C[output_row * N + output_col] = acc;
```

The most important point is that `output_row` and `output_col` are fixed for the lifetime of this thread:

- `output_row` identifies the target row of A that the thread must read.
- `output_col` identifies the target column of B that the thread must read.
- Together, `(output_row, output_col)` identifies the single output element of C that the thread must write.
- Only `k` changes inside the loop. It walks across the selected row of A and down the selected column of B.

The tensors in this example are passed to the kernel as flat pointers. Although we think of A, B, and C as two-dimensional matrices, each contiguous tensor is stored as a one-dimensional sequence in row-major order. For any matrix, we translate a two-dimensional coordinate into a flat memory offset using generic position names:

```text
flat offset = matrix_row_index × matrix_column_count + matrix_column_index
```

The generic names above change meaning for each access. For A they become `(output_row, k)`, for B they become `(k, output_col)`, and for C they become `(output_row, output_col)`.

#### Reading across one row of A

A has shape `M × K`, so every row contains `K` elements. Its flat index is:

```cpp
A[output_row * K + k]
```

During this thread's loop, `output_row` stays fixed while `k` changes from `0` to `K - 1`:

- `output_row * K` skips all complete rows before the selected row.
- `+ k` selects the next column within that row.
- Increasing `k` by one advances to the next contiguous element of A.

The access pattern is therefore:

```text
A[output_row, 0], A[output_row, 1], ..., A[output_row, K - 1]
```

#### Reading down one column of B

B has shape `K × N`, so every row contains `N` elements. Its flat index is:

```cpp
B[k * N + output_col]
```

Here, `output_col` stays fixed while `k` changes:

- `k * N` skips `k` complete rows of B.
- `+ output_col` selects the same target column within each row.
- Increasing `k` by one advances the flat memory offset by `N` elements, not by `output_col`.

Conceptually, this moves down one column of B:

```text
B[0, output_col], B[1, output_col], ..., B[K - 1, output_col]
```

The multiplication and addition inside the loop can therefore be written mathematically as:

```text
C[output_row, output_col] = Σ A[output_row, k] × B[k, output_col]
                            k
```

`acc` stores this running sum. It is private to the current thread and will typically be kept in a register rather than global memory.

#### Writing the result to C

C has shape `M × N`, so each of its rows contains `N` elements. Once the loop completes, the thread converts its output coordinate into C's flat index:

```cpp
C[output_row * N + output_col] = acc;
```

- `output_row * N` skips all complete rows before the target row.
- `+ output_col` selects the target column.
- `= acc` writes the completed dot product to that one output element.

The memory for C was already allocated by `torch::empty({M, N}, a.options())`; this line does not allocate more memory. It only calculates the destination offset and stores the result there.

For a concrete example, suppose `output_row = 2`, `output_col = 1`, `K = 3`, and `N = 4`. This thread reads:

```text
A indices: 2×3+0 = 6, 2×3+1 = 7, 2×3+2 = 8
B indices: 0×4+1 = 1, 1×4+1 = 5, 2×4+1 = 9
```

It accumulates:

```text
acc = A[6] × B[1] + A[7] × B[5] + A[8] × B[9]
```

Finally, it writes the result to:

```text
C index = output_row × N + output_col = 2×4+1 = 9
```

That flat offset corresponds to the two-dimensional output element `C[2, 1]`.

## Takeaways and scope

This naive matrix-multiplication kernel provides a concrete starting point for understanding how CUDA maps parallel work onto a GPU.

### What we learned

- A CPU uses a relatively small number of powerful cores, while a GPU is designed to run large numbers of similar operations in parallel.
- Multiplying A with shape `M × K` by B with shape `K × N` produces C with shape `M × N`.
- A CUDA launch contains a grid of thread blocks, and each block contains multiple threads.
- In this kernel, each thread owns one output coordinate, `(output_row, output_col)`.
- `output_row` selects one row from A, `output_col` selects one column from B, and `k` walks through the values used in their dot product.
- Contiguous matrices are stored in row-major order, so two-dimensional coordinates must be converted into flat offsets:

```text
A offset = output_row × K + k
B offset = k × N + output_col
C offset = output_row × N + output_col
```

- Grid dimensions use ceiling division so the launch covers matrices whose dimensions are not exact multiples of `BLOCK`.
- The kernel's bounds check makes the extra threads in partially filled edge blocks exit safely.

### What this post does not cover

This implementation is intentionally designed for clarity rather than speed. It does not yet cover:

- Shared-memory tiling and reuse of values from A and B
- Global-memory coalescing and detailed memory-access efficiency
